Domain 1: Prepare Agent Architecture & SDLC Processes

3 subtopics — Understand what makes software agents "agentic," how they integrate into the software development lifecycle, and how to configure observability and control over their autonomous behavior.

1.1 Integrate Agents into the SDLC

What Makes an AI System "Agentic" vs. "Assistant"

The exam draws a clear line between an assistant and an agent. An assistant responds to a single prompt — you ask it to write a function, it writes a function, and it's done. An agent is fundamentally different: it maintains goals across multiple steps, decides which actions to take, uses tools to interact with external systems, creates durable artifacts (branches, commits, pull requests, files), and iterates on feedback from those actions.

Assistant (Non-Agentic)
  • Single prompt → single response
  • Suggests code, does not execute it
  • No tool use beyond generation
  • No persistent state between turns
  • User manually applies suggestions
Agent (Agentic)
  • Maintains goals across many steps
  • Decides which actions to take next
  • Uses tools: file I/O, GitHub API, shell, MCP
  • Creates durable artifacts (branches, PRs)
  • Iterates based on feedback (CI, reviews)
Key Exam Concept

The defining characteristic of an agentic system is its ability to autonomously decide and execute multi-step actions toward a goal, creating lasting changes in the codebase. If it only suggests — it's an assistant. If it acts — it's an agent.

Steps Agents Can Perform in the SDLC

Agents can participate in nearly every phase of the software development lifecycle. The exam expects you to know which phases are well-suited for agent automation and which require human oversight:

  • Code generation: Creating new files, writing functions, scaffolding entire features from issue descriptions. The agent reads the issue, plans the implementation, writes code, and pushes it to a feature branch.
  • Code review: An agent can review PRs for style consistency, potential bugs, missing tests, or security issues. It leaves inline comments just like a human reviewer.
  • Testing: Generating unit tests, integration tests, running test suites, and reporting results. Agents can identify untested code paths and write tests to cover them.
  • Dependency updates: Scanning for outdated dependencies, creating PRs with version bumps, running tests to verify compatibility (similar to what Dependabot does, but with agentic reasoning about breaking changes).
  • Deployment: Triggering deployment pipelines, monitoring rollout health, performing rollbacks if metrics degrade.
  • Documentation: Generating or updating docs based on code changes, keeping READMEs in sync, writing changelog entries.

Common Anti-Patterns

The exam tests your ability to identify when agent usage goes wrong. Memorize these anti-patterns:

Anti-PatternDescriptionMitigation
Over-autonomy Agent acts without any human review gates — merges PRs, deploys to production without checks. Required approvals, branch protection, status checks before merge.
Context pollution Stale or conflicting context accumulates, causing the agent to make decisions based on outdated information. Context pruning, freshness checks, re-reading current state before acting.
Goal drift Agent gradually diverges from the original task — starts fixing "one more thing," refactoring unrelated code. Scoped task definitions, explicit success criteria, boundary enforcement.
Missing traceability No audit trail of what the agent did or why — commits lack context, no PR descriptions, no linked issues. Require meaningful commit messages, PR descriptions, issue linking.
Scope creep Agent exceeds the boundaries of its assigned task — modifies files outside its scope, changes configuration it shouldn't touch. File/directory scoping, CODEOWNERS, restricted tool permissions.
Anti-Pattern Warning

Over-autonomy and missing traceability are the two most dangerous anti-patterns in production. Every agent action should be traceable to a commit, PR, or workflow run. Every high-impact action should have a human review gate.

Defining Inputs, Outputs, and Success Criteria

A well-configured agent has clearly defined boundaries for each task:

  • Inputs: The issue description, requirements documents, context files (like copilot-instructions.md), existing code for reference, test fixtures, environment configuration.
  • Outputs: Feature branches, pull requests, code changes, test files, documentation updates, SARIF scan results, deployment artifacts.
  • Success criteria: All tests pass, no new security vulnerabilities (clean CodeQL/secret scanning), code review approved, performance benchmarks met, coverage thresholds maintained. These should be defined before the agent starts work.
# Example: Well-defined agent task specification
Task: Implement user authentication endpoint
Inputs:
  - Issue #142 (requirements)
  - /src/api/ (existing API patterns)
  - /tests/api/ (test patterns)
Outputs:
  - Branch: feature/auth-endpoint
  - PR with description and linked issue
  - Source files in /src/api/auth/
  - Tests in /tests/api/auth/
Success Criteria:
  - All existing tests still pass
  - New endpoint has >= 80% test coverage
  - CodeQL scan: zero new alerts
  - Secret scanning: clean
  - PR approved by CODEOWNERS

1.2 Define Boundaries Between Planning, Reasoning, and Action

The Plan → Act → Evaluate Lifecycle Loop

Agentic workflows are not linear. They follow a cyclical loop:

Plan
→
Act
→
Evaluate
→
Plan
...

The agent plans what to do, acts (writes code, creates a PR), evaluates (reads CI results, review feedback), and then plans again based on that evaluation. This cycle continues until the task meets its success criteria or the agent escalates to a human.

Planning Artifacts

When an agent plans, it should produce inspectable planning artifacts that humans can review:

  • Structured plans in PR descriptions: A checklist of what the agent intends to do, with scope, success criteria, and rollback paths.
  • Linked issues: The plan references the issue(s) it's addressing, maintaining traceability.
  • Checklists with scope/success criteria/rollback paths: Explicitly stating what's in-scope, what done looks like, and what to do if things go wrong.
## Agent Plan — PR #347

### Scope
- Add rate limiting middleware to /api/v2/* endpoints
- Update existing tests to cover rate limit responses

### Success Criteria
- [ ] Rate limit returns 429 with Retry-After header
- [ ] Existing API tests pass
- [ ] New rate limit tests have > 90% branch coverage
- [ ] CodeQL scan clean

### Rollback Path
- Revert this PR (no database migrations involved)
- Rate limiting config is env-var driven, can be disabled via RATE_LIMIT_ENABLED=false

Acting: What Agents Do

The "Act" phase involves the agent making durable changes:

  • Creating branches (git checkout -b feature/rate-limit)
  • Changing files (writing, editing, deleting source code)
  • Pushing commits (with meaningful commit messages)
  • Opening or updating pull requests
  • Responding to review feedback (addressing comments, pushing fixes)

Evaluating: How Agents Learn From Results

After acting, the agent evaluates by reading signals from the development environment:

  • Workflow runs: Did the CI pipeline pass? Which tests failed?
  • Status checks: Are all required checks green?
  • Code review feedback: What did reviewers say? Are there requested changes?
  • Security signals: Code scanning results (CodeQL), secret scanning alerts, dependency vulnerability alerts (Dependabot), SARIF uploads from third-party tools.
Key Exam Concept

SARIF (Static Analysis Results Interchange Format) is the standard format for reporting static analysis results to GitHub. When an agent runs a scanner (CodeQL or any third-party tool), the results are uploaded as SARIF files to GitHub's code scanning API. The agent then reads these results as evaluation signals.

Option A: Plan-First PR vs. Option B: Plan + Execution in Same PR

Option A: Plan-First PR

The agent opens a PR with only a plan — no code changes. A human reviews and approves the plan. Only after approval does the agent implement.

  • Best for high-risk work (schema changes, security-sensitive code, infrastructure)
  • Adds latency — waiting for plan approval
  • Maximum safety and alignment
Option B: Plan + Execution in Same PR

The agent includes both the plan (in the PR description) and the implementation (in the code changes) in a single PR.

  • Best for low-risk, fast iteration (bug fixes, dependency bumps, documentation)
  • Faster turnaround
  • Reviewer evaluates plan and code together

Enforcing Planning Boundaries

How do you prevent an agent from skipping the planning phase and jumping straight to code?

  • Read-only planning agents: A dedicated agent with only read access to the repository. It can analyze the issue and produce a plan, but it physically cannot write code. A separate agent with write access implements the plan.
  • Explicit handoff to implementation agents: The planning agent produces a structured plan and creates an issue or updates a PR description. A different agent (or the same agent in a different mode) picks it up for implementation.
  • Tool gating in orchestrators: The orchestration layer only grants write tools (file editing, git push) after a planning phase is complete and reviewed.
  • "Plan mode" workflows: The agent is configured via copilot-instructions.md to always output a plan first and wait for approval before proceeding.

Configuring Agent Planning Behavior

You configure how Copilot and other agents handle planning through instruction files:

# .github/copilot-instructions.md

## Planning Requirements
- Before writing any code, output a structured plan as a PR comment
- Include: scope, files to modify, success criteria, rollback path
- Wait for a human to approve the plan by commenting "approved"
- If the plan is rejected, revise based on feedback and resubmit
- Never skip the planning phase for changes touching /src/core/ or /infrastructure/
Key Exam Concept

The file .github/copilot-instructions.md is the repo-level configuration for GitHub Copilot agent behavior. It's the primary mechanism for controlling how the agent plans, acts, and self-constrains. Expect questions about what belongs in this file.

Validating Agent Plans Before Execution

Validation can happen through multiple mechanisms:

  • Human review: A required approval on the plan before the agent proceeds.
  • Automated checks: A workflow that validates the plan structure (does it include rollback paths? does it specify success criteria?).
  • Scope validation: Ensuring the plan doesn't touch files outside its designated scope.
  • Risk assessment: Automated classification of the plan's risk level, routing high-risk plans for additional review.

1.3 Configure Observability and Control for Autonomous Agents

Autonomy Levels

The exam defines a spectrum of autonomy. You need to match the right autonomy level to the situation. These map directly to GitHub Copilot's interaction modes:

LevelCopilot ModeDescriptionWhen to Use
Fully autonomous Agent + auto-merge Agent acts, merges, deploys without any human interaction. Only for extremely low-risk, well-tested, reversible operations (e.g., auto-fixing lint errors).
Supervised autonomous Agent mode (standard) Agent acts autonomously but a human reviews output before merge/deploy. Standard development tasks — feature PRs, bug fixes, dependency updates. Most common level.
Human-in-the-loop Agent mode with approval gates Agent proposes, human approves at key decision points during execution. Higher-risk tasks — schema changes, infrastructure modifications, security-related code.
Human-led Ask mode Human drives the process; agent assists with specific sub-tasks on request. Novel, unprecedented, or compliance-critical work where the agent lacks sufficient context.

Inspectable Artifacts

For any level of autonomy, you need to be able to inspect what the agent did. The exam expects you to know these inspectable artifacts:

  • Agent plans in PR descriptions: The plan the agent generated, visible to all reviewers.
  • Commit messages: Each commit should explain what was changed and why, providing a decision trail.
  • Workflow logs: GitHub Actions logs showing every step the agent executed, including tool calls and their results.
  • SARIF reports: Structured security scan results uploaded to the repo's code scanning dashboard.

Human Intervention Points

GitHub provides several built-in mechanisms for requiring human intervention:

  • PR reviews: Require one or more approvals before a PR can be merged. This is the most common intervention point for agent-generated code.
  • Required approvals: Configurable number of approving reviews needed.
  • CODEOWNERS: Specific files or directories require review from designated owners. If an agent modifies /src/auth/, the security team automatically gets tagged.
  • Branch protection rules: Enforce status checks, require approvals, prevent force pushes, restrict who can push to the branch.
  • Rulesets: GitHub's newer, more flexible system for branch/tag policies. Can be layered and applied at org level.
# CODEOWNERS file example
# These owners will be required reviewers for agent-generated changes

/src/auth/          @security-team
/infrastructure/    @platform-team @security-team
/src/api/billing/   @billing-team
*.sql               @database-team
Dockerfile          @platform-team

Balancing Speed vs. Safety

The exam tests a nuanced understanding: not every action needs the same level of oversight. The goal is to minimize approvals that don't materially reduce risk.

  • Auto-approve documentation-only PRs (low risk, easily reversible).
  • Require one approval for standard feature PRs.
  • Require multiple approvals for security-sensitive or infrastructure changes.
  • Use CODEOWNERS to route reviews to the right people, not just any people.
  • Fast-track changes that have clean CI, clean scans, and only touch well-tested areas.
Key Exam Concept

The exam asks you to right-size human intervention. Over-approving wastes time and creates bottlenecks. Under-approving introduces risk. The right answer usually involves classifying changes by risk level and applying proportional oversight — CODEOWNERS for sensitive areas, required checks for everything, manual approval only where it adds real value.

2.1 Select and Configure Agent Tools

Types of Tools

Agents interact with the world through tools. The exam categorizes tools into several types:

Tool TypeDescriptionExamples
GitHub API REST and GraphQL APIs for interacting with repos, issues, PRs, checks, releases. Create a PR, list issues, update a check run, read file contents, post a review comment.
File system Read, write, create, delete files in the working directory or repository checkout. Read package.json, write new source files, edit configuration.
Shell/Terminal Execute commands in a shell environment — build tools, test runners, linters. npm test, docker build, eslint ., git diff
External APIs Third-party services the agent calls via HTTP — monitoring, notification, deployment. Slack notifications, PagerDuty alerts, cloud provider APIs.
MCP servers Model Context Protocol servers that expose tools in a standardized format (covered in detail in 2.2). GitHub MCP server, custom database MCP server, Jira MCP server.

Tool Identification: Matching Tools to Task Requirements

When configuring an agent for a task, you select tools based on what the task requires:

  • Need to read issue descriptions? → GitHub API (issues endpoint)
  • Need to modify source code? → File system tools
  • Need to run tests? → Shell/terminal tools
  • Need to create a PR? → GitHub API (pulls endpoint)
  • Need to query a database? → MCP server or external API
  • Need to send a notification? → External API (Slack, Teams, email)

Tool Configuration in copilot-instructions.md

You define what tools an agent should use and how via configuration files:

# .github/copilot-instructions.md

## Available Tools
- Use the GitHub API for all PR and issue operations
- Use the file system to read and write source code
- Use the shell to run `npm test` and `npm run lint`
- Do NOT use shell commands to directly call `git` — use the GitHub API instead

## Tool Constraints
- Never execute `rm -rf` or any destructive shell commands
- Only read files within /src/ and /tests/ directories
- Do not modify files in /config/ or /.github/workflows/ without explicit approval
- API calls should use the minimum required scope (read-only when possible)

Tool Permissions: Read-Only vs. Read-Write

A core principle is least privilege. An agent should have the minimum permissions needed for its task:

  • Read-only: Appropriate for analysis agents (code review, security scanning, report generation). The agent can read files, issues, and PRs but cannot create or modify them.
  • Read-write: Necessary for implementation agents that need to create branches, push code, and open PRs. Should still be scoped to specific repos and branches.
  • Branch-scoped: Agent can only write to feature branches, never to main or protected branches.
  • Directory-scoped: Agent is restricted to specific directories within the repo.
Key Exam Concept

Least privilege for agent tools means: give read-only access by default, escalate to read-write only for the specific resources the task requires, and scope write access to the narrowest possible boundary (specific branch, specific directory). This principle applies to GitHub API tokens, file system access, and shell permissions.

2.2 Configure MCP Servers

What Is MCP (Model Context Protocol)?

MCP is a standard protocol for connecting AI clients (like GitHub Copilot) to external tools and services. Think of it as a universal adapter: instead of each AI tool having custom integrations for each service, MCP provides a standardized way for clients to discover, invoke, and get results from tools.

Key Exam Concept

Model Context Protocol (MCP) sits between the AI client and the underlying system. The client doesn't need to know the implementation details of the tool — it just calls the MCP server's standardized interface. This is similar to how a REST API abstracts away a database, except MCP is specifically designed for AI tool use.

MCP Server Architecture

An MCP server sits between the AI client and the underlying system it exposes:

AI Client (Copilot)
→
MCP Server
→
Underlying System (GitHub, DB, etc.)

The MCP server exposes tools in a structured format that the AI client can understand — it provides tool names, descriptions, parameter schemas, and return types. The client can discover available tools, call them with parameters, and receive structured results.

MCP Transports: stdio vs. HTTP

MCP supports two transport types. Knowing the difference is critical for the exam:

stdio Transport (Local Servers)
  • The client spawns the MCP server as a subprocess
  • Communication via stdin/stdout (no network involved)
  • Most common transport for local MCP servers
  • Server runs as long as the client runs, exits when client exits
  • Config specifies a command and optional args
HTTP Transport (Remote Servers)
  • Server runs independently, client connects via HTTP/HTTPS URL
  • Used for remote/hosted MCP servers (like GitHub's)
  • Server persists independently of the client
  • Supports authentication (OAuth, tokens)
  • Config specifies a url
Important for the Exam

stdio is NOT the same as "local HTTP." A local MCP server using stdio is spawned as a child process and communicates via stdin/stdout — there is no HTTP involved, no localhost URL, no port. HTTP transport is for remote servers accessed over the network. The exam may test whether you know that local servers typically use stdio, not HTTP.

Local vs. Remote MCP Servers

Local MCP Server
  • Runs on developer's machine
  • Access to local resources (files, databases, local services)
  • Custom setup per developer
  • Good for local-only tools or development-specific integrations
  • Transport: typically stdio (spawned as subprocess)
Remote MCP Server
  • Hosted service, accessible over the network
  • Less setup per developer — consistent across the team
  • Centrally managed permissions and updates
  • GitHub MCP server is remote: https://api.githubcopilot.com/mcp/
  • Transport: HTTP (connects via URL)

The GitHub MCP Server

GitHub provides an official MCP server that connects Copilot to repos, issues, PRs, and more. This is the most important MCP server for the exam:

  • URL: https://api.githubcopilot.com/mcp/
  • Provides tools for reading/writing repo contents, managing issues, creating PRs, checking workflow status.
  • Remote is recommended — avoids local setup, consistent credentials, managed by GitHub.

Adding a Remote MCP Server in VS Code

The exam tests the exact steps to add an MCP server. Here's the procedure for a remote server (like GitHub's):

  1. Open Copilot Chat in VS Code
  2. Switch to Agent mode
  3. Click the Tools button (wrench icon)
  4. Select Configure tools
  5. Click Add MCP server
  6. Select HTTP as the transport type
  7. Enter the URL: https://api.githubcopilot.com/mcp/
  8. Authenticate when prompted (GitHub OAuth flow)

This adds a configuration to your VS Code settings:

// .vscode/settings.json — Remote MCP server (HTTP transport)
{
  "mcp": {
    "servers": {
      "github": {
        "type": "http",
        "url": "https://api.githubcopilot.com/mcp/"
      }
    }
  }
}

Adding a Local MCP Server (stdio)

Local MCP servers typically use the stdio transport. The client spawns the server as a subprocess and communicates via stdin/stdout. No port or URL is involved:

// .vscode/settings.json — Local MCP server (stdio transport)
{
  "mcp": {
    "servers": {
      "my-local-tool": {
        "type": "stdio",
        "command": "npx",
        "args": ["-y", "@my-org/mcp-server-mydb"]
      }
    }
  }
}

// Another example — a Python-based local MCP server
{
  "mcp": {
    "servers": {
      "my-python-tool": {
        "type": "stdio",
        "command": "python",
        "args": ["-m", "my_mcp_server"],
        "env": {
          "DATABASE_URL": "postgres://localhost:5432/mydb"
        }
      }
    }
  }
}
Key Exam Concept

MCP uses two transports: stdio for local servers (spawned as subprocesses, configured with command + args) and HTTP for remote servers (configured with a url). The GitHub MCP server is remote (HTTP). Most community/local MCP servers use stdio. Know both configuration formats.

MCP Registries

An MCP registry is a central catalog of MCP servers for discovery and standardization. It allows organizations to control which MCP servers are available to their developers.

  • Default registry: The GitHub MCP Registry — the built-in catalog.
  • Custom registries: Organizations can run their own registries. Requirements:
    • Must follow the MCP Registry v0.1 spec.
    • Must expose HTTPS endpoints (e.g., GET /v0.1/servers to list available servers).
    • Must include proper CORS headers for browser-based tools to discover servers.
  • Self-hosting options: Fork and self-host the open-source MCP Registry, run via Docker, or build a custom implementation.
  • Azure API Center can act as a managed MCP registry for organizations using Azure.

MCP Allow Lists

Organizations and enterprises can control which MCP servers are permitted through allow lists. This is a policy control:

Policy LevelBehavior
Allow all No restrictions. Any MCP server (local or remote) can be used.
Registry only Only MCP servers listed in the configured registry are permitted. Even local servers must be registered.

Configuration steps for organization MCP policy:

  1. Go to Enterprise settings (or Organization settings)
  2. Navigate to AI controls (under Policies or Settings)
  3. Find the MCP section
  4. Click Enable
  5. Set the registry URL (or use the default GitHub registry)
  6. Choose the restriction level: "Allow all" or "Registry only"
Important for the Exam

When "Registry only" is enabled, even local MCP servers must be listed in the configured registry. This catches many people — they assume local servers bypass the policy, but they don't. The policy is enforced at the client level.

2.3 Integrate Agents Within Development Environments

Execution Context Evaluation

Before deploying an agent, you need to evaluate its execution context — what it can see and do. The context determines the agent's capabilities and limitations:

  • What files/repos can it access? Scoped to a single repo, multiple repos, or entire org?
  • What APIs can it call? GitHub API, external services, internal tools?
  • What environment variables are available? Secrets, configuration, feature flags?
  • What network access does it have? Can it reach external services, databases, internal systems?

Repository-Scoped Agents

A common pattern is to scope an agent to a single repository. This limits its context and capabilities:

  • Agent can only read/write files in that repo.
  • Agent can only interact with issues and PRs in that repo.
  • Configuration is stored in the repo's .github/copilot-instructions.md.
  • Prevents cross-repo contamination (agent modifying unrelated code).

CI Workflow Agents (GitHub Actions as Orchestration)

Agents can be triggered and orchestrated through GitHub Actions workflows. This is a major exam topic — using workflows to invoke agents on specific events:

# .github/workflows/agent-pr-review.yml
name: Agent PR Review
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  pull-requests: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run agent review
        uses: my-org/copilot-review-action@v1
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          instructions: |
            Review this PR for:
            - Security vulnerabilities
            - Missing test coverage
            - Code style violations
            Post findings as PR review comments.

Common trigger events for agent workflows:

  • workflow_dispatch — Manual trigger (human kicks off the agent).
  • issues — Triggered when an issue is opened, labeled, assigned (agent starts working on assigned issues).
  • pull_request — Triggered on PR events (agent reviews, runs checks, responds to feedback).
  • schedule — Cron-based (agent runs periodic maintenance — dependency updates, stale issue cleanup).

Branch-Based Scope

A critical safety principle: agents should never operate directly on main/default branch. Always on feature branches:

  • Agent creates a feature branch from the default branch.
  • All changes happen on the feature branch.
  • Changes only reach the default branch through a reviewed, approved PR.
  • This gives humans a review gate before any agent code enters production.

Autonomous Actions

What agents do autonomously within their scoped environment:

  • Creating branches from the default branch.
  • Committing code changes to feature branches.
  • Opening pull requests with structured descriptions.
  • Responding to review comments with code fixes.
  • Updating PRs based on CI failures (fix failing tests, re-push).

Environment-Specific Constraints

Agents may have different configurations depending on the environment:

  • Development: Broader access, more tools available, faster iteration.
  • Staging: Restricted to read-only for production data, deployment gated.
  • Production: Highly restricted — typically no direct agent access, changes only via deployed and reviewed code.

Copilot Cloud Agent Firewall Customization

The Copilot cloud agent runs in GitHub's infrastructure. You can customize its network access:

  • Control which external URLs the agent can reach.
  • Block access to internal systems that shouldn't be reachable from the cloud agent.
  • Allow specific API endpoints needed for the agent's tasks.
  • Configured at the organization or enterprise level.
Key Exam Concept

Copilot cloud agent is GitHub's hosted execution environment for agents. Unlike the local Copilot agent mode in your IDE, the cloud agent runs on GitHub's servers. It has its own firewall rules, network policies, and execution constraints. You configure its access at the org/enterprise level, not per-developer.

2.4 Operate Agents with Safe Execution Paths

Error Handling

Agents encounter errors. The exam tests how well-designed agents handle failures gracefully:

  • Try/catch patterns: Wrap tool calls in error handling. If a GitHub API call fails, catch the error, log it, and decide the next action (retry, skip, escalate).
  • Graceful degradation: If a non-critical tool is unavailable (e.g., linter fails to run), the agent should continue with available tools and note the limitation in the PR description.
  • Meaningful error messages: When an agent encounters an error it can't recover from, it should post a clear PR comment explaining what went wrong, what it tried, and what a human needs to do.
# Pseudocode: Agent error handling pattern
try:
    test_result = run_tool("shell", "npm test")
    if test_result.exit_code != 0:
        # Tests failed — analyze and fix
        failures = parse_test_output(test_result.stdout)
        for failure in failures:
            fix = generate_fix(failure)
            apply_fix(fix)
        # Re-run tests after fix
        retest = run_tool("shell", "npm test")
        if retest.exit_code != 0:
            # Still failing — escalate to human
            post_pr_comment("Tests still failing after attempted fix. "
                          "Need human review. See workflow run for details.")
            escalate()
except ToolError as e:
    post_pr_comment(f"Agent encountered an error: {e.message}. "
                   "Pausing for human review.")
    escalate()

Retries

When transient errors occur (API rate limits, network timeouts), agents should retry intelligently:

  • Exponential backoff: Wait 1s, 2s, 4s, 8s between retries — don't hammer a failing service.
  • Max retry limits: Don't retry forever. Set a maximum (e.g., 3 retries) and escalate after that.
  • Idempotency checks: Before retrying a write operation, verify the previous attempt didn't partially succeed. Example: before retrying "create PR," check if a PR already exists for that branch.

Rollbacks

When an agent's changes cause problems, rollback mechanisms should be available:

  • git revert: Creates a new commit that undoes the agent's changes. Preserves history.
  • Branch reset: For feature branches, reset to the state before the agent's changes.
  • Environment rollback: If the agent triggered a deployment, roll back to the previous version.
  • Configuration rollback: If the agent modified configuration, revert the config changes.

Escalation Paths

When an agent should hand off to a human:

  • Failed retries: After exhausting retry attempts, the agent should stop and ask for help.
  • Security alerts: If a code scan reveals vulnerabilities in the agent's code, escalate immediately.
  • Out-of-scope changes: If the agent detects it needs to modify files outside its scope, stop and request expanded permissions.
  • Ambiguous requirements: If the agent can't determine the correct approach from the issue description, ask for clarification.
  • Conflicting instructions: If copilot-instructions.md conflicts with the issue description, escalate for resolution.

Traceability

Every agent action must be traceable. This is non-negotiable for audit and debugging:

  • Every code change linked to a commit with a descriptive message.
  • Every commit linked to a PR with a description of the plan and outcome.
  • Every PR linked to an issue (the original request).
  • Every tool invocation logged in a workflow run.
  • The complete chain: Issue → Plan → Branch → Commits → PR → CI Runs → Review → Merge.
Key Exam Concept

Think of agent output like a junior developer's PR. You wouldn't merge a junior dev's PR without review, without CI passing, without understanding what was changed and why. Apply the same contributor model to agents: review everything, require checks, maintain an audit trail.

Edit (deprecated March 2026) Surgical inline edits. Copilot makes targeted changes to specific files you select. Limited — file edits only, no terminal, no tools Small, focused refactors. Being replaced by agent mode's capabilities.

Key Exam Concept

Agent mode is the only mode that is truly "agentic" — it autonomously decides what to do, uses tools, and iterates. Ask mode is purely conversational (human-led). Edit mode was a middle ground for inline changes but is deprecated in favor of agent mode's broader capabilities.

How Agent Mode Works

When you give agent mode a task, it follows the Plan → Act → Evaluate loop automatically:

  1. Plans: Analyzes the request, identifies which files to read and modify, determines the steps needed.
  2. Selects context: Autonomously opens and reads relevant files — you don't have to manually select them.
  3. Acts: Creates/edits files, runs terminal commands (build, test, lint), invokes MCP tools.
  4. Evaluates: Reads command output, checks for errors, reviews test results.
  5. Iterates: If tests fail or errors occur, it modifies its approach and tries again.

Terminal Command Approval Flow

Agent mode can run terminal commands, but potentially risky commands require user approval:

  • When the agent wants to run a shell command, it surfaces the command in the chat for you to review.
  • You can approve the command (it runs), reject it (agent replans), or edit it before running.
  • Read-only commands (like cat, ls, grep) may run automatically depending on settings.
  • Destructive or write commands (rm, git push, npm install) typically require approval.
  • This approval flow is the human-in-the-loop safety mechanism for agent mode.
Important for the Exam

Terminal command approval is a key safety feature of agent mode. The agent cannot bypass this — it always surfaces risky commands for review. This is different from the cloud agent, which runs in an isolated environment with its own security model.

MCP Integration in Agent Mode

Agent mode accesses external tools through MCP servers:

  • MCP servers configured in .vscode/settings.json are available as tools in agent mode.
  • The agent discovers available tools from connected MCP servers and can invoke them as needed.
  • Example: the GitHub MCP server gives agent mode access to issues, PRs, and repo operations without leaving the IDE.
  • You can enable/disable specific MCP tools via the Tools button in the chat panel.

2.6 Copilot Extensions

What Are Copilot Extensions?

Copilot Extensions allow developers to extend Copilot Chat's capabilities with custom tools and integrations. They are GitHub Apps that users invoke via @mention in Copilot Chat (e.g., @my-extension do something).

There are two types of extensions:

Agents (Full Control)
  • Take full control of the request/response cycle
  • Can use custom LLMs (not limited to Copilot's model)
  • Implement custom logic, orchestration, and conversation management
  • Integrate with the Copilot API or any other AI provider
  • Handle the entire conversation flow themselves
  • Best for complex, domain-specific integrations
Skillsets (Lightweight)
  • Define API endpoints that Copilot can call
  • The platform handles routing, prompt crafting, and response formatting
  • Developer only needs to define the API and its schema
  • Uses Copilot's built-in LLM (no custom model needed)
  • Simpler to build and maintain
  • Best for straightforward tool integrations

Agents vs. Skillsets Comparison

AspectAgentsSkillsets
Control over LLM Full — can use any LLM or the Copilot API None — platform uses Copilot's built-in model
Conversation management Extension manages the entire conversation Platform manages conversation, extension provides data
Complexity to build Higher — implement request handling, LLM calls, response streaming Lower — define API endpoints and schemas
Prompt crafting Extension crafts its own prompts Platform crafts prompts from API descriptions
Deployment GitHub App — hosted by the developer GitHub App — hosted by the developer (API only)
Invocation @agent-name in Copilot Chat @skillset-name in Copilot Chat

How Extensions Work

  1. Developer creates a GitHub App and configures it as a Copilot Extension.
  2. For agents: implement a webhook endpoint that receives the user's message and returns a response (can call custom LLMs).
  3. For skillsets: define API endpoints with OpenAPI-style descriptions so the platform knows when and how to call them.
  4. Users install the extension and invoke it via @mention in Copilot Chat.

What Are Agent Skills?

Agent skills are folders containing instructions, scripts, and resources that Copilot automatically loads when they are relevant to the current task. They let you package domain-specific knowledge and tooling that the agent can discover and use.

Skill Locations

Skills can be defined at project level (shared with the team) or personal level (just for you):

  • The instructions.md file is the core — it tells the agent what to do, what constraints apply, and what scripts/resources are available in the skill folder.
  • Skills are discoverable via the gh skill command, which lists available skills and their descriptions.

2.8 Copilot SDK

What Is the Copilot SDK?

The Copilot SDK allows developers to embed Copilot's agentic core into any application. It provides programmatic access to the same engine that powers Copilot CLI and agent mode, so you can build custom tools that plan, invoke tools, edit files, and run commands.

Technical Preview

The Copilot SDK is currently in technical preview. The API surface may change. However, the exam study guide references it, so you should understand its purpose and capabilities.

Core Capabilities

  • Tool invocation: Call tools (file system, shell, APIs, MCP servers) programmatically.
  • File editing: Read and modify files in a working directory, with diff-based editing.
  • Command execution: Run shell commands and process their output.

Domain 3: Manage Memory, State & Execution

3 subtopics — How agents remember things, maintain state across interactions, detect when their context drifts from reality, and share state across tools and environments.

3.1 Agent Memory Strategies

Short-Term Memory

Short-term memory is the agent's working context within a single session or task:

  • Conversation context: The messages exchanged so far in the current session.
  • Current task state: What the agent is working on right now — the issue, the plan, what it's already done.
  • Tool call results: Outputs from tools invoked during this session.
  • Scope: Limited to the current session. When the session ends, short-term memory is lost.

Short-term memory is the agent's "working memory" — analogous to holding information in your head while you work on something. It's limited by the context window of the underlying model.

Long-Term Memory

Long-term memory persists across sessions and tasks:

  • copilot-instructions.md: The primary long-term memory mechanism for GitHub Copilot agents. Stored in the repo, persists indefinitely, shared across all sessions.
  • .github/copilot-instructions.md: Repo-level instructions — accessible to the agent every time it interacts with that repo.
  • Persistent configuration: Settings, preferences, and constraints that the agent applies consistently.
  • Learned patterns: Over time, agents can be configured to reference past decisions (stored in issues, PR descriptions, or dedicated memory files).
# .github/copilot-instructions.md — Acts as long-term memory

## Project Context
- This is a Node.js 20 + TypeScript project
- We use ESLint with our custom config
- Tests use Vitest, not Jest
- Database is PostgreSQL via Prisma ORM
- API follows REST conventions (not GraphQL)

## Coding Conventions
- Use functional components (no classes)
- Error handling: always use custom AppError class
- Logging: use the shared logger from /src/lib/logger.ts
- File naming: kebab-case for files, PascalCase for components

## Past Decisions
- We chose Prisma over TypeORM (PR #89 — type safety was the deciding factor)
- Rate limiting uses token bucket, not sliding window (Issue #112)
- Auth uses JWT with short-lived access tokens + refresh tokens (PR #134)

External Memory

Beyond the agent's built-in memory, external systems serve as memory stores:

  • Issue trackers: Issues contain requirements, decisions, and discussion history.
  • Wikis: Project documentation, architecture decisions, runbooks.
  • Documentation: README files, API docs, design docs.
  • Databases: Structured data the agent can query for historical context.
  • File-based state: JSON/YAML files in the repo tracking agent state (e.g., a .agent-state.json tracking what's been done).

Scoping Memory to Task-Relevant Information

A common failure mode is context window pollution — loading too much irrelevant information into the agent's context, crowding out what it actually needs. Best practices:

  • Only load files relevant to the current task.
  • Summarize large documents rather than including them verbatim.
  • Use targeted queries (search for specific function names, not entire directories).
  • Prune conversation history — remove resolved threads, keep open items.

Memory Expiration, Pruning, and Reset

  • Expiration: Short-term memory naturally expires when a session ends. Long-term memory in instructions files persists until manually updated.
  • Pruning: Periodically review and remove outdated information from copilot-instructions.md. Old conventions that no longer apply can mislead the agent.
  • Reset: For a fresh start, clear the agent's conversation history. In more extreme cases, remove or rewrite the instructions file.
Key Exam Concept

The exam distinguishes between short-term (session-scoped), long-term (repo-scoped, via copilot-instructions.md), and external (issues, wikis, databases) memory. Expect questions asking you to identify the right memory strategy for a given scenario. Rule of thumb: if it needs to persist across sessions, it's long-term. If it's specific to this task, it's short-term. If it's shared across the organization, it's external.

3.2 Persist Agent State and Manage Context Drift

Durable Artifacts as State

Agents don't have built-in persistent storage between sessions. Instead, they use GitHub's existing artifact system to persist state:

  • PR descriptions as state: The PR description contains the agent's plan, current progress, and remaining tasks. When the agent resumes, it reads the PR description to understand where it left off.
  • Issue comments as progress logs: The agent posts progress updates as issue comments. This creates a chronological log of what's been done.
  • Commit messages as decision records: Each commit message explains not just what changed but why, creating a history of decisions.
## PR #412 — Agent State (auto-updated)

### Plan
- [x] Create rate limiting middleware
- [x] Add configuration via environment variables
- [ ] Write unit tests for rate limiter
- [ ] Integration test with API endpoints
- [ ] Update API documentation

### Current State
Step 3 of 5. Middleware implemented and tested locally.
Awaiting test write pass.

### Context
- Using token bucket algorithm (per Issue #112 decision)
- Configuration: RATE_LIMIT_WINDOW=60, RATE_LIMIT_MAX=100
- Dependencies added: none (implemented in-house)

Resuming Work

When an agent needs to pick up where it left off (e.g., after a CI failure, after receiving review feedback, or after a session timeout):

  1. Read the PR description for the current plan and progress.
  2. Read recent issue comments for progress updates.
  3. Read the branch's commit history for what's already been done.
  4. Read CI results for the current state of tests and checks.
  5. Read review comments for feedback that needs to be addressed.

Context Drift Detection

Context drift occurs when the agent's understanding of the codebase diverges from reality. This happens when:

  • Stale file references: The agent's plan references files that have been renamed, moved, or deleted by another developer or agent.
  • Outdated dependencies: The agent is working with dependency versions that have been updated in the meantime.
  • Changed requirements: The issue was updated with new requirements after the agent started working, but the agent is still following the original requirements.
  • Concurrent changes: Another developer or agent modified the same files the agent is working on.

Correcting Drift

  • Re-reading current state: Before making changes, always git pull or re-fetch the latest file contents. Never rely on cached state.
  • Refreshing context: Re-read the issue description, PR comments, and linked documents to check for updates.
  • Comparing plan vs. actual: Diff the planned changes against the current state of the code. If the code has changed since the plan was created, update the plan.
  • Merge conflict detection: If the agent's branch has conflicts with the default branch, resolve them before continuing.
Common Exam Scenario

The exam may present a scenario where an agent is working on a PR and another developer merges a conflicting change to main. The correct answer involves the agent detecting the drift (via merge conflict or failing tests), pulling the latest changes, resolving conflicts, and re-evaluating its plan.

3.3 Ensure Continuity Across Tools and Environments

Sharing Agent State

When multiple tools or environments are involved, agents need to share state consistently:

  • Via Git (branches/commits): The code on a branch is the primary shared state. Any tool or environment that can read the branch has access to the agent's work.
  • Via GitHub API (issues/PRs/comments): Structured data in issues and PRs serves as a communication channel between agents, tools, and humans.
  • Via artifacts: GitHub Actions artifacts can store files (logs, reports, build outputs) that persist across workflow runs.

Preventing Conflicting Context

When multiple agents or tools operate on the same repo, conflicts can arise:

  • Single source of truth: Designate one location as the authoritative state (usually the PR description or a specific issue). All agents read from and write to this location.
  • Merge conflict resolution: When two agents modify the same file, standard git merge conflict resolution applies. The orchestrator should detect conflicts and either auto-resolve (for trivial conflicts) or escalate.
  • Lock mechanisms: For critical operations (like deployments), use a locking mechanism to prevent two agents from acting simultaneously. GitHub environments with protection rules can serve this purpose.

Preventing Stale Context

  • Always read current state before acting: Before modifying a file, re-read it. Don't rely on a cached version from an earlier step.
  • Validate assumptions: If the agent's plan assumes a function signature exists, verify it before writing code that calls it.
  • Timestamp-based freshness checks: Compare the last-modified time of the branch or PR with the agent's last read time. If it's changed, refresh before acting.
Key Exam Concept

The exam tests your understanding of state sharing in multi-tool scenarios. The correct answer almost always involves using Git as the source of truth (branches and commits) with GitHub API objects (PRs, issues) as the coordination layer. Avoid storing critical state in ephemeral locations (environment variables, in-memory caches) that don't persist.

Domain 4: Perform Evaluation, Error Analysis & Tuning

3 subtopics — Defining what "success" means for agents, analyzing failures and their root causes, and tuning agent behavior based on results.

4.1 Define Success Criteria and Evaluation Signals

Expected Outcomes

Before an agent starts a task, you must define what success looks like. These are concrete, measurable outcomes:

  • Tests pass: All existing tests still pass, and new tests cover the changes.
  • No new vulnerabilities: Code scanning (CodeQL), secret scanning, and dependency scanning report zero new alerts.
  • Code quality metrics met: Linting passes, complexity thresholds maintained, no new tech debt.
  • Review approved: At least one (or more, depending on policy) human reviewer approves the PR.

Operational Constraints

Beyond functional outcomes, agents operate within constraints:

  • Time limits: An agent should complete its task within a reasonable timeframe. A stuck agent burning compute for hours is a resource waste.
  • Resource limits: CPU, memory, API rate limits, token usage limits.
  • Scope boundaries: The agent should only modify files and resources within its assigned scope.

Qualitative vs. Quantitative Signals

Quantitative Signals
  • Test coverage percentage
  • Number of vulnerabilities (0 = pass)
  • Build time
  • Lines of code changed
  • Performance benchmarks (response time, throughput)
  • Lint error count
Qualitative Signals
  • Code readability and clarity
  • Documentation quality
  • Design pattern adherence
  • Naming consistency
  • Appropriate abstraction level
  • Reviewer subjective assessment

Aligning Evaluation with Development Intent

Evaluation should answer not just "does it compile?" but "does it solve the problem?":

  • Does the implementation match the requirements in the issue?
  • Does it handle edge cases mentioned in the requirements?
  • Is the solution appropriate for the context (not over-engineered or under-engineered)?
  • Does it integrate well with the existing codebase (consistent patterns, conventions)?

Automated Scanning Tools

GitHub provides several built-in tools that serve as evaluation signals:

ToolWhat It ScansOutput Format
CodeQL Source code for security vulnerabilities, bugs, code quality issues SARIF (uploaded to code scanning)
Dependabot Dependencies for known vulnerabilities Dependabot alerts, auto-generated PRs
Secret scanning Committed code for exposed secrets (API keys, tokens, passwords) Secret scanning alerts
Third-party SARIF Any static analysis tool that outputs SARIF can upload results to GitHub's code scanning API SARIF
Key Exam Concept

CodeQL, Dependabot, and secret scanning are the three pillars of GitHub's built-in security scanning. An agent evaluates its own output by reading the results of these tools after pushing code. A clean scan is a pass signal; new alerts are a fail signal requiring the agent to fix the issue or escalate.

4.2 Analyze Agent Failures and Root Causes

Failure Identification Sources

When an agent's output is wrong or incomplete, you investigate using these sources:

  • Workflow logs: The GitHub Actions run log shows every step, including tool invocations and their outputs. This is usually the first place to look.
  • Agent plans: Compare what the agent planned to do with what it actually did. Did it follow its own plan?
  • Execution traces: Detailed logs of tool calls in order — which tools were called, with what parameters, and what they returned.
  • Output diffs: Compare the agent's code changes against the expected outcome. Where does the diff diverge from expectations?
  • CI artifacts: Test results, coverage reports, build logs — what specifically failed?

Root Cause Categories

Agent failures fall into three broad categories. The exam tests your ability to classify a failure into the right category:

CategorySymptomsExamples
Reasoning errors The agent chose the wrong approach, misunderstood the requirements, or made a logical mistake.
  • Implemented deletion instead of soft-delete
  • Used wrong data structure (array instead of map)
  • Misinterpreted "update" as "replace"
Tool misuse The agent used the wrong tool, called a tool with incorrect parameters, or called tools in the wrong order.
  • Used git push --force instead of a regular push
  • Called API endpoint with wrong HTTP method
  • Tried to merge before CI completed
Context/environment issues The agent had stale context, missing permissions, or the environment changed unexpectedly.
  • Built against old dependency versions
  • Missing API token caused 401 errors
  • File was renamed by another developer
Key Exam Concept

When the exam describes an agent failure, ask yourself: Did the agent think wrong (reasoning error), do the wrong thing (tool misuse), or have the wrong information (context/environment)? The fix depends entirely on the category: refine instructions for reasoning errors, restrict or reconfigure tools for tool misuse, improve state management for context issues.

4.3 Tune Agent Behavior

Revising Instructions

The primary tuning mechanism is updating the agent's instruction files:

  • Update copilot-instructions.md: Add constraints, clarify conventions, provide examples of correct behavior.
  • Refine prompts: Make instructions more specific. Instead of "write good tests," say "write tests using Vitest with describe/it blocks, cover happy path and at least 2 error paths."
  • Add constraints: If the agent over-reaches, add explicit boundaries. "Do not modify files outside /src/api/" or "Always use the existing error handling pattern from /src/lib/errors.ts."
# Before tuning — vague instruction
Write tests for the new feature.

# After tuning — specific instruction
Write tests using Vitest. Structure:
- One describe block per function
- Test happy path
- Test at least 2 error/edge cases
- Use existing test fixtures from /tests/fixtures/
- Mock external API calls using vi.mock()
- Assert using expect().toEqual() or expect().toThrow()
- Target 80%+ branch coverage for new code

Refining Memory

  • Adjust what's stored: If the agent is making decisions based on outdated information, update or remove stale entries in copilot-instructions.md.
  • Clear stale memory: Remove references to deprecated patterns, old dependencies, or renamed files.
  • Improve memory scoping: If the agent loads too much context, narrow what it reads. Use targeted file references instead of broad directory includes.

Refining Tool Usage

  • Restrict tool access: If the agent misuses a tool, remove it from the available tools list or add guardrails around its use.
  • Expand tool access: If the agent is missing capabilities it needs, add new tools or MCP servers.
  • Change tool ordering: Configure the agent to run linting before pushing (catch issues earlier) or run tests before creating a PR.
  • Improve tool descriptions: In MCP server configurations, update tool descriptions to help the agent choose the right tool for each task.
Key Exam Concept

Tuning is an iterative process: observe failure → classify root cause → apply targeted fix → re-evaluate. Reasoning errors are fixed with better instructions. Tool misuse is fixed with tool configuration changes. Context issues are fixed with memory and state management improvements. The exam wants you to match the fix to the root cause category.

Domain 5: Orchestrate Multi-Agent Coordination

4 subtopics — Patterns for running multiple agents together, observability in multi-agent systems, handling failures when multiple agents are involved, and managing agent lifecycles.

5.1 Operate Multi-Agent Workflows

Orchestration Patterns

When multiple agents collaborate on a project, they can be organized in different patterns. The exam expects you to know when to use each:

Sequential Pattern (Pipeline)

Agent A (Plan)
→
Agent B (Implement)
→
Agent C (Test)
→
Agent D (Review)

Each agent completes its work before the next starts. Agent A's output is Agent B's input. This is the simplest pattern — no concurrency concerns. Use for tasks with clear dependencies between phases.

# .github/workflows/sequential-agents.yml
name: Sequential Agent Pipeline
on:
  issues:
    types: [labeled]

jobs:
  plan:
    if: github.event.label.name == 'agent-task'
    runs-on: ubuntu-latest
    steps:
      - name: Agent A — Generate plan
        uses: my-org/planning-agent@v1
        # Output: plan.json artifact

  implement:
    needs: plan
    runs-on: ubuntu-latest
    steps:
      - name: Agent B — Implement plan
        uses: my-org/coding-agent@v1
        # Input: plan.json from previous job

  test:
    needs: implement
    runs-on: ubuntu-latest
    steps:
      - name: Agent C — Write and run tests
        uses: my-org/testing-agent@v1

  review:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: Agent D — Review output
        uses: my-org/review-agent@v1

Parallel Pattern

Multiple agents work simultaneously on independent tasks:

Agent A (Frontend)
→
Agent B (Backend)
→
Agent C (Tests)

All three work concurrently on different parts of the codebase. This is faster but requires agent isolation to prevent conflicts.

Hierarchical Pattern

Orchestrator Agent
↓
Specialist A
→
Specialist B
→
Specialist C

An orchestrator agent breaks down the task and delegates sub-tasks to specialist agents. The orchestrator monitors progress and handles coordination.

Fan-Out / Fan-In Pattern

One agent spawns multiple sub-tasks (fan-out), which are processed by multiple agents. Results are collected and combined (fan-in) by the original or a dedicated collector agent.

# Fan-out: One orchestrator creates 5 sub-issues
# Each sub-issue is picked up by an independent agent
# Fan-in: Orchestrator waits for all 5 to complete, then merges results

Fan-out:
  Orchestrator -> creates Issue #201 (module-auth)
  Orchestrator -> creates Issue #202 (module-billing)
  Orchestrator -> creates Issue #203 (module-notifications)

Parallel execution:
  Agent-A works on #201
  Agent-B works on #202
  Agent-C works on #203

Fan-in:
  Orchestrator detects all 3 PRs merged
  Orchestrator creates integration PR combining all changes
  Orchestrator runs integration tests

Agent Isolation for Parallel Execution

When agents run in parallel, they need isolation to prevent conflicts:

  • Separate branches: Each agent works on its own feature branch. No two agents modify the same branch.
  • Separate working directories: In CI, each agent job has its own checkout of the repo.
  • Sandboxed environments: Each agent runs in its own container or VM, with independent file systems, environment variables, and network access.
  • File-level locking: If agents must work in the same directory, use a locking mechanism to prevent concurrent edits to the same file.

Conflict Detection and Resolution

  • Overlapping code changes (merge conflicts): When two agents modify the same file, merging their branches will produce a conflict. The orchestrator should detect this and either auto-resolve (if the changes are in different parts of the file) or escalate.
  • Duplicated effort: Two agents independently solving the same problem. The orchestrator should prevent this by clearly scoping each agent's task.
  • Contradictory outputs: Two agents produce solutions that disagree (e.g., one adds a feature, the other removes it). The orchestrator must detect the contradiction and resolve it (usually by escalating to a human).
Key Exam Concept

Know when to use each orchestration pattern. Sequential for dependent phases. Parallel for independent tasks (but requires isolation). Hierarchical when a coordinator is needed. Fan-out/fan-in for tasks that can be decomposed, processed independently, and recombined.

5.2 Configure Observability for Multi-Agent Behavior

Artifacts Suitable for Review

In multi-agent workflows, observability is harder because actions are distributed. You need consolidated artifacts:

  • Per-agent logs: Each agent produces its own execution log (tool calls, decisions, errors). These are typically stored as workflow run logs or artifacts.
  • Combined workflow summaries: A summary view that shows all agents' activities in one place — which agents ran, what they produced, how long they took, and whether they succeeded.
  • Diff reports: A consolidated diff showing all changes made by all agents, making it easy to review the aggregate impact.

Documenting Decisions, Handoffs, and Outcomes

In multi-agent systems, the handoff between agents is a critical point that must be documented:

  • Decisions: When an agent makes a significant decision (choosing an approach, skipping a step), it should log the decision and the reasoning in a PR comment or workflow log.
  • Handoffs: When Agent A passes work to Agent B, the handoff should be explicit. Agent A's output (a branch, an artifact, a PR update) is Agent B's input. Both sides log the handoff.
  • Outcomes: Each agent documents its final output — what was accomplished, what remains, any issues encountered.

Post-Hoc Analysis

After a multi-agent workflow completes, analysis should cover:

  • Reconstructing what happened: Timeline of all agent actions, in chronological order, across all agents.
  • Identifying bottlenecks: Which agent took the longest? Was any agent idle waiting for another?
  • Measuring effectiveness: Did the multi-agent approach save time vs. a single agent? Were there redundant efforts?
  • Improving for next time: What would you change about the orchestration pattern, agent scoping, or handoff mechanisms?

5.3 Detect and Respond to Multi-Agent Failures

Types of Multi-Agent Failures

Failure TypeDescriptionDetection Signal
Failed execution An agent crashes, times out, or exhausts resources (memory, API limits). Non-zero exit code, workflow failure, timeout alert.
Partial completion Some agents succeed while others fail. The overall task is incomplete. Mixed status in the orchestrator's tracking — some sub-tasks done, others not.
Stalled agent An agent is running but making no progress — infinite loop, deadlock, waiting on an unavailable resource. No new commits/comments for an extended period, high resource usage with no output.

Recovery Patterns

  • Rollback (revert all agent changes): When the multi-agent workflow produces an inconsistent state, revert all changes from all agents and start over. This is the safest but most expensive option.
  • Human-in-the-loop (pause and ask): Pause the entire workflow, alert a human, and wait for instructions. The human decides whether to continue, rollback, or take a different approach.
  • Retry individual agents: If only one agent failed and the failure is transient (network issue, rate limit), retry just that agent while keeping the others' results.
  • Graceful degradation: If a non-critical agent fails (e.g., the documentation agent), continue the workflow without it and note the gap.
# Recovery decision tree
if all_agents_failed:
    rollback_all_changes()
    alert_human("Complete failure — rollback executed")
elif critical_agent_failed:
    if is_transient_error(failure):
        retry_agent(failed_agent, max_retries=3)
    else:
        pause_workflow()
        alert_human("Critical agent failed — needs investigation")
elif non_critical_agent_failed:
    log_gap(f"{failed_agent.name} failed — continuing without it")
    continue_workflow()
elif agent_stalled:
    if stall_duration > timeout_threshold:
        kill_agent(stalled_agent)
        alert_human("Agent stalled and was terminated")
Common Exam Scenario

The exam often presents a scenario where Agent A succeeds but Agent B fails in a parallel workflow. The correct answer depends on whether Agent B's work is critical (must rollback and retry) or non-critical (can continue with graceful degradation). Always assess criticality before choosing a recovery pattern.

5.4 Manage Agent Lifecycle in Multi-Agent Workflows

Adding Agents

When adding a new agent to an existing multi-agent workflow:

  • Integrate without disruption: The new agent should be added in a way that doesn't require stopping or restarting running agents.
  • Define its scope clearly: What tasks will it handle? What files/resources does it own? How does it interact with existing agents?
  • Test in isolation first: Run the new agent on a test branch/repo before integrating into the production workflow.
  • Update the orchestrator: The orchestrator needs to know about the new agent — its capabilities, inputs, outputs, and where it fits in the workflow.

Updating Agents

Agent updates include version changes, configuration updates, and prompt improvements:

  • Rolling updates: Update agents one at a time, verifying each works before updating the next. Safest approach for critical workflows.
  • Blue-green deployment: Run the old and new versions of an agent simultaneously. Route some tasks to the new version, verify results, then switch all traffic. Best for high-risk updates.
  • Version management: Pin agent versions in workflow files (e.g., uses: my-org/coding-agent@v2.1.0) so updates are explicit and reversible.
  • Config changes: Update copilot-instructions.md or agent configuration files. These take effect on the next agent invocation.

Retiring Agents

When an agent is no longer needed:

  • Graceful shutdown: Allow the agent to complete any in-progress tasks before stopping it.
  • Preserve audit trail: Don't delete the agent's history — its PRs, commits, issues, and logs are part of the project's record.
  • Redirect responsibilities: If the retired agent handled certain tasks, either assign them to another agent or to a human.
  • Maintain workflow continuity: Removing an agent from a pipeline shouldn't break downstream agents. Update the orchestrator configuration.
Key Exam Concept

Agent lifecycle management mirrors application lifecycle management. The exam expects you to apply familiar concepts (rolling updates, blue-green deployments, graceful shutdown) to agents specifically. A key point: always preserve the audit trail when retiring an agent — its history matters for traceability.

6.1 Define Autonomy Levels

Risk Classification

Before setting an autonomy level, classify the risk of the agent's actions across three dimensions:

Risk DimensionQuestionExamples
Operational risk Can it break the build, cause downtime, or degrade performance? Modifying CI config, changing database schemas, touching deployment scripts.
Security risk Can it expose secrets, create vulnerabilities, or weaken access controls? Modifying auth code, handling encryption, managing API keys, changing permissions.
Compliance risk Does it violate regulatory requirements, licensing, or organizational policies? Handling PII, modifying audit logging, changing data retention, license-incompatible dependencies.

The Autonomy Spectrum

Rather than a strict numbered scale, think of agent autonomy as a practical spectrum that maps to real GitHub Copilot modes and configurations:

Autonomy LevelCopilot ParallelBehaviorAppropriate For
Human-led Ask mode (read-only Q&A) Human does all the work. Agent only answers questions and suggests approaches — no code changes, no tool use. Exploring unfamiliar code, learning, extremely high-risk situations.
Human-in-the-loop Edit mode / Agent mode with approval gates Agent proposes edits or actions; human approves each significant step before execution. Agent cannot act without sign-off. High-risk, compliance-sensitive work. Security-critical code changes. New or unproven agents.
Supervised autonomous Agent mode (standard) / Cloud agent with PR review Agent autonomously plans, writes code, runs tools, opens PRs — but a human reviews and merges. Agent iterates on feedback. Standard development. This is the most common and recommended level for production use.
Auto-merge with checks Cloud agent + auto-merge rules Agent can merge its own PR if all automated checks pass (CI, scans, code quality). No human review required. Low-risk, well-defined tasks: dependency bumps, lint fixes, doc updates.
Fully autonomous End-to-end agent pipeline Agent operates without any human interaction, including deployment and monitoring. Extremely low-risk, highly reversible actions only. Rare in practice.
Critical Exam Point

Supervised autonomous (agent acts, human reviews before merge) is the default recommendation for most production agent use cases. It balances speed with safety. If you're unsure which level to choose on the exam, this is usually the right answer for standard development work. The key GitHub features enforcing this are branch protection rules and required PR reviews.

Exam Terminology Note

The GitHub documentation and study guide use terms like "autonomous" for agent mode and "in the loop" for edit mode. On the exam, focus on matching the behavior description (does the agent need approval? can it merge?) rather than memorizing a specific numbered scale. The practical distinction is: who holds the final approval — the agent, the automated checks, or a human?

Right-Sizing Human Interventions

The goal is to match the intervention level to the risk level:

  • Documentation-only change? Auto-merge with checks is fine.
  • New API endpoint? Supervised autonomous (human reviews the PR before merge).
  • Authentication system changes? Human-in-the-loop (approve each step) or at minimum supervised autonomous with security team CODEOWNERS.
  • Database migration in production? Human-in-the-loop or fully human-led.

Balancing Delivery Speed with Compliance and Responsible AI

The exam tests your understanding that there's a tension between speed and safety. The right approach:

  • Automate everything that can be automated safely (CI, scans, linting).
  • Require human judgment only where it adds value (novel decisions, security-sensitive changes, compliance).
  • Use risk classification to route: low-risk tasks get fast-tracked, high-risk tasks get thorough review.
  • Responsible AI standards: agents should not make decisions that have ethical implications without human oversight (e.g., content moderation, user-facing language, accessibility).

6.2 Implement Guardrails and Human-in-the-Loop

Actions Requiring Human Judgment

Not every action should be automated. The exam expects you to identify scenarios that require human review:

  • Irreversible changes: Database migrations that drop columns, permanent data deletion, removing API endpoints that external clients depend on.
  • Security-sensitive operations: Changes to authentication/authorization code, encryption implementations, API key management, RBAC configurations.
  • Compliance-related decisions: Changes affecting data privacy (GDPR, CCPA), audit logging, license compliance, regulatory reporting.
  • Novel/unprecedented situations: The agent encounters something not covered by its instructions or the existing codebase. When in doubt, escalate.

Blocking Policy Violations with GitHub Features

GitHub provides several mechanisms to enforce guardrails:

Branch Protection Rules

# Branch protection for 'main' branch

  Require pull request reviews:
    Required approving reviews: 2
    Dismiss stale PR approvals: true
    Require review from CODEOWNERS: true

Rulesets

Rulesets are GitHub's newer, more flexible alternative to branch protection rules:

  • Can be applied at the organization level (affect all repos in the org).
  • Can be layered — multiple rulesets can apply to the same branch.
  • Support bypass lists — specific users or teams can bypass specific rules.
  • Support tag rules — not just branches.
  • Can enforce merge methods (squash only, rebase only).

Required Status Checks

Status checks are automated validation that must pass before a PR can be merged:

  • CI pipeline: Build + test suite must pass.
  • Code scanning (CodeQL): No new security alerts.
  • Secret scanning: No secrets detected in the code.
  • Custom checks: Any GitHub Actions workflow that reports a check status.
  • When configured as "required," these block merge until they pass — even for agents.

Least-Privilege Access

The principle of least privilege applied to agents:

  • Scoped tokens: Use fine-grained personal access tokens (PATs) or GitHub App tokens that only grant the permissions the agent needs.
  • Minimal permissions in workflows: Set permissions in workflow YAML to the narrowest scope needed.
  • Environment-specific access: The agent gets different permissions in dev vs. staging vs. production.
# Minimal permissions for an agent that reviews PRs
permissions:
  contents: read        # Read repo files
  pull-requests: write  # Post review comments
  # No: issues write, deployments, packages, etc.

Explicit Authorization for Irreversible/Compliance-Sensitive Changes

  • Required approvals: Set a higher approval threshold for sensitive paths (2+ reviewers for /src/auth/).
  • Deployment gates: GitHub Environments with required reviewers. The agent cannot deploy until a designated person approves.
  • Environment protection rules: Wait timers (delay deployment by N minutes for human review window), required reviewers, branch restrictions.
# GitHub Environment: production
Protection rules:
  Required reviewers: @org/platform-leads (at least 1)
  Wait timer: 15 minutes
  Deployment branches: only 'main'

# This means an agent CANNOT deploy to production without:
# 1. Code being on 'main' branch (requires PR merge)
# 2. A platform lead approving the deployment
# 3. A 15-minute window for additional review

Preserving Execution Velocity

Guardrails shouldn't make everything slow. The goal is to be fast where it's safe:

  • Auto-approve low-risk changes: Auto-merge PRs that only change documentation, comments, or test fixtures (when all checks pass).
  • Fast-track well-scoped agents: Agents with a proven track record on specific task types can get streamlined review.
  • Focus human attention on high-risk: Use CODEOWNERS and rulesets to route human review to where it matters most.
  • Parallelize checks: Run CI, scans, and code quality checks in parallel to minimize wait time.
Key Exam Concept

The exam wants you to demonstrate that guardrails are proportional to risk. The correct answer is never "block everything" (too slow) or "allow everything" (too risky). It's always: classify the risk, apply the right level of oversight, and automate what can be automated safely. Use branch protection rules, CODEOWNERS, required status checks, and environment protection rules as your toolkit.
